# 需求分析

## 分析摘要

本需求是现有发布能力的启动入口扩展。核心不是新建更新系统，而是把设置加载、自动检查、确认弹窗和已有下载安装动作串成一个可观察、可取消且不阻断启动的前端流程。

## 资料来源与阅读口径

- 最高优先级：用户原始要求与已批准的交互设计。
- 现有能力基线：`release.ts`、设置 store、根组件、设置页更新流程、Tauri updater 配置和中英文 locale。
- 冲突口径：用户确认的启动交互优先；已有手动更新与托盘检查行为必须保持兼容。
- 未读取资料：无外部 PRD、原型或 API 文档；更新协议由仓库现有实现定义，不在本需求重新解释。

## 已确认范围

- 设置成功加载后读取 `autoCheckUpdates`。
- 开关开启时，每个根组件生命周期自动检查一次。
- 新版可用时显示全局确认弹窗。
- 用户确认后执行现有下载、安装和自动重启。
- 安装失败后在弹窗内反馈并允许重试。
- 添加中英文文案和自动化覆盖。

## 非目标

- 不修改 GitHub Release、`latest.json`、更新签名或发布流水线。
- 不增加后台定时轮询、跳过版本、强制更新或发布说明展示。
- 不重构设置页现有手动检查 UI。
- 不改变设置 schema、IPC 或 Rust 服务。

## 已确认口径与不变量

- 自动检查必须受持久化设置控制，不能在设置加载前凭默认值触发。
- 检查失败和已是最新均静默，不影响应用初始化。
- 安装必须由用户显式确认。
- 安装进行中不可关闭确认弹窗。
- 安装成功后的重启继续由 `ReleaseActionsPort.installUpdate()` 保证。
- 手动和自动检查复用同一个 release actions 实例及其待安装 update 缓存。

## 系统职责与边界

- Vue 根应用：拥有启动编排和弹窗可见状态。
- 设置 store：作为 `autoCheckUpdates` 的可信来源，拥有加载状态。
- release actions：拥有检查、下载、安装和重启，不向 UI 泄露 Tauri `Update` 对象。
- 弹窗组件：只表达确认、pending 和 error，不直接调用 updater。
- Tauri/GitHub Release：既有外部依赖，只复用，不修改。

## 来源支持的行为清单

| 行为簇 | 触发 | 分支 | 用户可见结果 |
| --- | --- | --- | --- |
| 启动检查 | 设置 ready 且开关开启 | latest / error | 静默结束 |
| 新版确认 | 检查返回 available | 等待选择 | 显示当前版本和新版本 |
| 稍后处理 | 用户点击稍后 | 关闭 | 返回当前页面 |
| 立即更新 | 用户点击立即更新 | installing | 锁定弹窗并显示安装中 |
| 安装失败 | install 抛错 | error | 保留弹窗、显示错误、可重试 |
| 安装成功 | install 完成 | relaunch | 由现有服务重启应用 |

## 面向开发者的行为细化

- 自动检查由根级协调逻辑触发，不依赖当前路由，任意页面都能显示弹窗。
- 设置为关闭、加载失败或组件已卸载时不得显示弹窗。
- 检查执行中无需可见 loading；只有发现新版后才进入用户可见状态。
- 弹窗初始焦点落在“稍后”安全操作，支持键盘焦点循环。
- 非安装态允许 Escape、遮罩和“稍后”关闭；安装态全部禁用。
- 安装错误使用稳定本地化文案，不展示插件或系统私有错误详情。
- 用户关闭后本次运行不重复自动提示；手动检查仍可单独工作。

## 隐含需求与隐藏假设

| 来源线索 | 隐含问题 | 当前口径 | 影响与处理 |
| --- | --- | --- | --- |
| 设置异步初始化 | 何时读取开关 | 已确认：ready 后 | 监听 store 状态和值，避免抢跑 |
| updater 缓存 pending update | 自动检查与安装是否同实例 | 已确认：复用注入实例 | 根组件使用同一 `ReleaseActionsPort` |
| 安装会重启 | pending 时能否关闭 | 已确认：不能 | 弹窗锁定交互 |
| 自动检查可能网络失败 | 是否阻断启动或提示 | 已确认：静默 | 捕获错误且不写全局错误状态 |

## 工作流与依赖判断

- 前置依赖是设置初始化；更新检查不得反向阻塞它。
- 新版信息来自 release actions 返回的 `UpdateCheckResult`。
- UI 安装动作依赖 release actions 内部保留最近一次 update。
- 手动检查和托盘检查是回归敏感邻接流程，但无需改变。

## 歧义与确认登记

无业务歧义。用户已确认立即更新的安装与重启语义；静默失败、稍后处理和重试规则已在批准设计中固定。

## 风险与约束

| 风险 | 触发 | 影响 | 保护方式 |
| --- | --- | --- | --- |
| 设置未加载即检查 | 根组件挂载 | 违背用户关闭选择 | 测试关闭与延迟加载分支 |
| 重复 watcher 触发 | store 多次更新 | 重复网络请求或弹窗 | 每生命周期一次性闩锁 |
| 自动检查错误泄漏 | 网络或插件失败 | 启动被打断 | 静默捕获并测试 |
| 安装态可关闭 | 用户按 Escape/点击遮罩 | 状态失联 | pending 锁定与组件测试 |
| 手动流程回归 | 共享 release 实例 | 设置页更新失效 | 保持端口不变并跑现有测试 |

## 阻塞项分级与处理口径

- 业务阻塞：无。
- 外部接口待补：无；仓库已有 updater endpoint 与签名配置。
- 非阻塞：真实新版端到端验证依赖后续发布一个更高版本，可在发布冒烟阶段完成。

## 减少二次确认提示

- spec 不再重开启动时机、静默失败、按钮语义或安装锁定决策。
- 实现只需在既有依赖注入和组件风格内选择最小边界。
- 验收必须覆盖关闭开关、latest、available、检查错误、安装失败和重试。

## 拆分策略

保持为单一功能模块“启动更新确认流程”。协调逻辑、确认弹窗和 locale 共同完成一个不可分割的用户流程，不拆成独立交付模块。

## 下游阶段信号

- page-design：需要，需定义全局模态的内容、状态和响应式行为。
- architecture-design：不需要；现有 release port、store 和依赖注入边界足够。
- requirement-splitting：形成一个顺序模块，完成后进入 page-design。
