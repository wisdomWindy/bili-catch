# 系统集成与发布架构设计

## 交付单元

- request: `bilicatch-v1-desktop`
- module: `system-release`
- source: `requirements/modules/system-release.md`

## 架构目标与范围

把现有 Tauri/Vue 桌面能力接入可发布产品：系统托盘、通知、文件与窗口行为、更新检查/签名验证、FFmpeg sidecar 注入，以及 Windows/macOS/Linux 产物配置。架构只覆盖系统集成和发布边界，不重新设计业务页面或下载业务。

触发条件：应用启动、任务状态通知、窗口关闭/拖拽文件、手动检查更新、安装确认、打包流水线运行。

## 上游输入与假设

- 复用现有 Tauri 2、Vue、Pinia、i18n、TaskManager、Settings 和音视频执行器。
- 发布渠道、签名私钥、图标源文件和可信 FFmpeg 二进制尚未提供，均作为外部发布输入，不在代码中伪造。
- 目标平台为 Windows NSIS/MSI、macOS DMG/App、Linux deb/rpm/AppImage，并生成 `latest.json` 与 `.sig`。

## 模块边界

```text
系统事件/窗口/托盘/通知 -> Tauri commands/plugins -> frontend settings/status
发布配置/sidecar -> Tauri bundler -> 平台产物 + updater metadata
updater metadata -> 签名校验 -> 用户确认 -> 安装/失败通知
```

系统集成层拥有平台副作用；前端只消费稳定的设置和通知状态；业务服务不直接调用托盘、窗口、更新器或打包器。

## 文件与目录结构

```text
src-tauri/
  capabilities/          # 最小化系统/更新/通知权限
  infrastructure/system/ # tray, notification, window, file-dialog adapters
  infrastructure/update/ # metadata fetch, signature verification, installer adapter
  services/system/       # typed system commands and lifecycle policy
  tauri.conf.json         # bundle targets, externalBin, updater config
  binaries/               # trusted platform sidecar inputs, never generated by code
src/features/system/     # frontend settings/status adapters only when needed
docs/.../system-release/ # architecture/spec/plan/verification/review evidence
```

## 依赖方向与职责

- `services/system` 依赖端口和稳定 DTO，不依赖具体平台 API。
- `infrastructure/system` 实现窗口、托盘、通知、文件对话框端口。
- `infrastructure/update` 实现更新元数据、签名和安装器边界，禁止向 UI 泄漏原始响应或 stderr。
- `src-tauri/lib.rs` 只做组合根和生命周期注册。
- 前端通过既有 Tauri invoke/event 适配层消费状态，不在组件内调用平台 API。

## 函数与公共入口

- `SystemLifecycle::on_startup()`：恢复窗口设置，初始化托盘/通知和 updater 检查。
- `SystemLifecycle::on_close_requested()`：根据设置最小化到托盘或退出；有活动任务时请求确认。
- `SystemLifecycle::notify_task_update()`：将任务终态映射为稳定通知文案。
- `UpdaterPort::check()`：拉取并校验版本元数据，返回 typed update state。
- `UpdaterPort::install()`：只接受已验证且用户确认的更新，失败返回稳定错误码。
- `SidecarLocator::locate()`：按平台解析已配置的 FFmpeg externalBin，缺失返回 E008。

## 状态归属与数据流

- 窗口位置/大小、关闭行为、通知开关归 `SettingsManager`；系统层只读并执行。
- updater 状态归系统服务：`idle -> checking -> available|up_to_date|failed -> installing -> installed|failed`。
- 用户确认是安装前唯一人工闸门；取消不改变已安装版本。
- sidecar 路径、版本和哈希只作为发布/运行时内部数据，不进入任务、checkpoint 或前端错误详情。

## 数据结构与类型策略

- Rust serde DTO 是 IPC 契约源；字段使用 camelCase 序列化。
- `UpdateState`、`WindowBehavior`、`NotificationKind`、`ReleaseArtifact` 使用显式 enum/struct，避免字符串状态。
- 平台产物使用配置表描述目标、文件扩展名、签名文件和安装入口；不在业务代码中拼接 shell 命令。
- 前端仅声明与 Rust DTO 对齐的最小类型，不扫描或引入无关 ambient declarations。

## 合同与适配器边界

- Tauri capability 文件是权限唯一来源，按命令/插件最小授权；不新增通配权限。
- 更新源必须 HTTPS、版本与平台匹配，签名验证在安装前完成。
- FFmpeg 通过 Tauri `externalBin` 注入，执行器继续复用现有 `FfmpegLocator`，不引入 shell。
- 原始更新响应、签名内容、私钥、stderr 和本地绝对路径不得进入 UI、日志或持久化任务数据。

## 模式决策与拒绝方案

- 使用 Adapter 隔离平台 API、Updater 和 Sidecar；使用组合根完成 Tauri 注册。
- 不引入插件市场、事件总线、跨平台工厂层或发布 DSL；目标平台差异保持在配置和基础设施边界内。
- 不新增业务路由或页面，系统能力沿用托盘、对话框、设置入口和通知。

## 可读性与维护护栏

- 单个生产文件超过 250 行进入 review，超过 350 行必须拆分。
- 平台副作用集中在 infrastructure；services 只编排 typed port。
- 所有失败路径必须有稳定错误码和清理策略；禁止原始 stderr/响应透传。
- externalBin、签名和产物配置必须由发布清单测试覆盖。

## 架构风险

- 缺少可信 sidecar、签名证书和图标源文件会阻塞真实发布验收。
- 各平台 updater 行为差异需在目标 runner 上验证，当前环境不能替代 macOS/Linux 实机。
- Tauri plugin 版本与 capability schema 可能受现有依赖锁定，实施前必须读取实际配置。

## 待确认架构问题

1. 发布服务 URL、签名公钥及证书保管位置。
2. Windows 采用 NSIS、MSI 或双产物默认策略。
3. macOS 签名/notarization 和 Linux 包签名是否纳入本次流水线。
4. 可信 `ffmpeg.exe` 及 macOS/Linux sidecar 的版本、哈希和许可证材料。
